---
title: Progress Bar v1 to v2
description: Migrate ProgressBar to ProgressBarV2 by separating progress geometry from its visual appearance.
---

## Overview

`ProgressBar` is deprecated in favor of `ProgressBarV2`. Values, ranges,
labels, accessibility labels, and the linear and circular presentations remain
available. The central migration is splitting v1’s overloaded visual API into
two independent choices:

- `variant` chooses the geometry: `LINEAR` or `CIRCULAR`.
- `appearance` chooses the fill style: `SOLID` or `SEGMENTED`.

This lets both appearances work consistently for both geometries and avoids
using `variant` for two different concerns.

## Quick migration

```tsx
// v1: a segmented linear bar
import {
    ProgressBar,
    ProgressBarSize,
    ProgressBarVariant,
} from '@juspay/blend-design-system'
;<ProgressBar
    value={65}
    min={0}
    max={100}
    size={ProgressBarSize.MEDIUM}
    variant={ProgressBarVariant.SEGMENTED}
    showLabel
    aria-label="Upload progress"
/>
```

```tsx
// v2: geometry and appearance are explicit
import {
    ProgressBarV2,
    ProgressBarV2Appearance,
    ProgressBarV2Size,
    ProgressBarV2Variant,
} from '@juspay/blend-design-system'
;<ProgressBarV2
    value={65}
    min={0}
    max={100}
    size={ProgressBarV2Size.MD}
    variant={ProgressBarV2Variant.LINEAR}
    appearance={ProgressBarV2Appearance.SEGMENTED}
    showLabel
    aria-label="Upload progress"
/>
```

## Breaking changes

### Rename the component and size enum members

**v1:** `ProgressBar` and `ProgressBarSize.SMALL`, `.MEDIUM`, `.LARGE`.

**v2:** `ProgressBarV2` and `ProgressBarV2Size.SM`, `.MD`, `.LG`.

The underlying size values remain `sm`, `md`, and `lg`; only the public enum
member names change. Map `SMALL` to `SM`, `MEDIUM` to `MD`, and `LARGE` to
`LG`. The default remains the medium size.

### Split v1 `variant` into `variant` and `appearance`

**v1:** `variant` combines shape and linear appearance:
`SOLID`, `SEGMENTED`, or `CIRCULAR`. The separate `type` prop chooses a solid
or segmented circular ring.

**v2:** `variant` is `LINEAR` or `CIRCULAR`, while `appearance` is `SOLID` or
`SEGMENTED` for either shape.

Use the following direct mappings:

```tsx
// v1 linear solid
variant={ProgressBarVariant.SOLID}

// v2 linear solid
variant={ProgressBarV2Variant.LINEAR}
appearance={ProgressBarV2Appearance.SOLID}

// v1 linear segmented
variant={ProgressBarVariant.SEGMENTED}

// v2 linear segmented
variant={ProgressBarV2Variant.LINEAR}
appearance={ProgressBarV2Appearance.SEGMENTED}

// v1 circular segmented
variant={ProgressBarVariant.CIRCULAR}
type={ProgressBarType.SEGMENTED}

// v2 circular segmented
variant={ProgressBarV2Variant.CIRCULAR}
appearance={ProgressBarV2Appearance.SEGMENTED}
```

Remove `ProgressBarType` and the `type` prop after converting circular bars.
The v2 defaults—linear and solid—match v1’s default solid linear bar.

### Review circular segmented visuals

**v1:** segmented circular progress uses butt stroke caps.

**v2:** circular progress uses round stroke caps for both appearances, with
segment dash lengths supplied by the v2 token contract.

The progress value and range do not change, but a segmented ring has a visibly
different finish. Snapshot or visually test circular segmented indicators,
especially at small sizes or wherever the old dash geometry was customized.

### Handle invalid ranges predictably

**v1:** values are clamped to `min` and `max`, but an equal or reversed range
can produce invalid percentage math or inverted ARIA bounds.

**v2:** reverses an inverted range before computing progress and uses 0% when
`min === max`.

Normal ranges need no migration. If a call site can receive a zero-length or
reversed range, v2 renders a stable empty state and reports ordered ARIA range
bounds. Keep domain validation in the caller when that state should instead be
treated as an error.

### Update custom tokens

**v1:** the component reads `PROGRESS_BAR` tokens. The linear style keys use
the old `ProgressBarVariant`, while circular styles use `ProgressBarType`.

**v2:** it reads `PROGRESS_BARV2`. Both linear and circular appearance keys use
`ProgressBarV2Appearance`, and v2 adds a linear gap token and a circular motion
token.

Rebuild token overrides for `PROGRESS_BARV2`; do not copy old paths directly.
Map old linear `solid` and `segmented` variants to `linear.*[appearance]`, and
old circular type keys to `circular.*[appearance]`. Review light and dark
themes as well as the new `sm`/`md`/`lg` enum keys.

## What continues to work

`value`, `min`, `max`, and `showLabel` keep their purpose and defaults. Values
are still clamped to the active range, the percentage label is still visual
only, and the progressbar element continues to expose `aria-valuenow`,
`aria-valuemin`, and `aria-valuemax`. Continue to provide `aria-label` or
`aria-labelledby` for a meaningful accessible name; when omitted, both
versions generate a percentage-based default name.

## V2 token migration

V2 uses a distinct token contract. Treat custom token overrides as a new API: move them to the V2 token contract, then review renamed, removed, and newly nested entries instead of copying V1 paths unchanged.

The component-specific token changes are called out above. For reference, compare the [V1 component tokens](/docs/components/progressbar#component-tokens) with the [V2 component token reference](/docs/components/progress-bar-v2#component-tokens).
