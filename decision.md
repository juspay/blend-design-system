# Decision record: SidebarV3 for the Juspay dashboard revamp

Status: Blend implementation verified by focused tests, lint, typecheck, and package build; Storybook rendering, ReScript binding, and rendered design comparison pending. Date: 2026-11-13.

## Goal and source of truth

Build a new, exported Blend `SidebarV3` that can reproduce the signed-off **Chin up (D)** sidebar in `../euler-design-demos/app/dashboard/`. Keep `SidebarV2` available with its current API and behavior. The eventual consumer is the ReScript `../juspay-portal`; its access checks, routes, account data, and configuration remain in that app.

The design reference is Euler's `app/sidebar/sidebar-page.tsx`, `look.tsx`, `quick-search.tsx`, `group-motion.tsx`, `ia.tsx`, and `app/shell.tsx`. The implementation baseline is Blend's `packages/blend/lib/components/SidebarV2/` and `Directory/`. The portal integration reference is `packages/common/src/components/blendComponents/BlendSidebar.res`, `packages/common/src/utils/BlendSidebarAdapter.res`, and `packages/common/src/components/SidebarTypes.res` in `../juspay-portal`.

This record is based on source inspection. Rendered desktop, collapsed, and mobile comparisons have **not yet been performed**; capture and review those before locking visual values or calling the implementation complete.

Verification on 2026-11-13: SidebarV3 tests 9/9 and SidebarV2 regression tests 74/74 passed; targeted ESLint, Blend TypeScript `--noEmit`, Vite build, and `check-dist` passed. The Vite declaration plugin reported an existing TS2742 portability diagnostic in `Directory/utils.ts` while the build still exited successfully. Storybook typecheck could not complete because its local dependencies were not linked; the browser connection could not open the Euler reference.

## Runtime hardcoding audit

- SidebarV3 receives navigation, merchant choices, strip content, search control, active route, and callbacks through props. Euler/Juspay names and routes appear only in Storybook and test fixtures.
- `data ?? []` is an empty fallback for V2's optional `data` prop, not a built-in menu. Internal maps and state objects hold expansion state.
- The default `100dvh` height and V2-compatible 50ms/0.2s toggle and width timing remain behavior defaults. The `[` shortcut is V3's documented default and can be overridden.
- Euler D's `#FCFCFD` surface, 48px strip, 16px strip padding, 16px corners, 8px merchant padding, 12px separator offset, 6px guide offset, and 150ms/200ms motion are V3 theme-token defaults. They are overridable through `SIDEBARV3`.
- Storybook sample arrays intentionally match SidebarV2's demonstration pattern. They are not imported by runtime code.

## Public API decision

- Export `SidebarV3` and `SidebarV3Props` from the package root. Add a separate `SIDEBARV3` component-token slot with light and dark defaults; do not rename or alter `SIDEBARV2`.
- Start from `SidebarV2Props` so existing generic `data`, expansion, selection, secondary rail, merchant, footer, mobile, and virtualization inputs remain available. Add `topStrip: ReactNode` and optional `sidebarSearch?: ReactNode`. The D reference passes strip content and omits `topbar`; keep the optional V2 topbar capability for other consumers without rendering two bars by default.
- Render `topStrip` in a labelled header region above the rounded application frame. Use V3 tokens for the 48px strip height, surface, and 16px top corners; calculate the inner layout height from the supplied overall `height` (default `100dvh`). A provided `topbar` remains inside the inner content frame.
- Render `sidebarSearch` between the reused `SidebarV2Header` and `Directory`, only when the primary panel is expanded or shown as an expanded hover preview. Give it a stable, scoped container instead of forcing consumers to manipulate the DOM.
- Keep props friendly to generated ReScript bindings: ordinary React slots, strings, booleans, callbacks, and the existing Directory types. Verify the generated signatures before publication.

## Implementation sequence

1. **Visual baseline:** Run the Euler demo and capture `/dashboard` at desktop expanded, desktop collapsed, nested open/selected, and mobile widths. Record exact geometry, colours, focus states, and motion; compare with the code values above. Inspect the signed-off route rather than an exploratory letter.
2. **Blend component:** Add `SidebarV3` beside V2. Share safe V2 internals where useful, but keep distinct exports, token namespace, styles, and tests. Implement the strip/frame, search slot, and scoped D styling. Use Directory's current controlled expansion; add a narrow Directory capability only where V3 cannot express the signed-off behavior. Preserve accessibility and reduced-motion handling.
3. **Reference and verification:** Add Storybook stories for signed-off D-shaped content plus collapsed, nested, mobile, and long-label states. Add focused interaction/accessibility tests for slots, height, expansion, selection, keyboard navigation, mobile, and motion completion. Run Blend lint, tests, and build; inspect rendered Storybook against the Euler captures.
4. **Release and Euler example:** Publish Blend and matching ReScript bindings. Upgrade Euler from its published Blend version, switch its locked `/dashboard` route to V3, and remove only the frame/search/styling/motion workarounds V3 replaces. Keep Euler's app-specific search palette, variant registry, navigation data, and actions. Run Euler typecheck, lint, build, and browser review.
5. **Portal migration plan:** In a separate portal change, adapt the already filtered `BlendSidebarAdapter` output to V3, supply strip/search/account slots, and gate the renderer with a dedicated rollout flag. Verify merchant, reseller, tenant, Juspay, and admin contexts; remote links, blacklists, mobile, active routes, and fallback to the existing sidebar. Do not change portal files as part of the Blend component implementation.

## Explicit exclusions and reasons

- **No hardcoded Euler/Juspay navigation or branding in Blend.** The portal builds its tree from ACL, user context, CAC flags, blacklists, and runtime Breeze tabs; hardcoding any of that would break other consumers.
- **No built-in command palette.** Euler's `ModalV2` palette and `TextInputV2` trigger search its own route index; the portal has its own `GlobalSearch`. V3 provides placement, not search data or routing.
- **No automatic V2 replacement.** V2 is used by existing consumers. A separate V3 export permits visual comparison and a controlled portal rollout.
- **No portal implementation in this work.** The current portal path uses the older `Sidebar` and generated ReScript bindings. It needs its own dependency release and application rollout after V3 is published.
- **No claim of pixel parity yet.** Source values and CSS are documented here; rendered comparison remains a required acceptance step.

## Acceptance criteria

- V3 visually matches signed-off Euler D at the captured widths and states, without global CSS, DOM insertion, or document-level click interception in Euler.
- V2's public API and tests continue to pass; V3 has its own exports, tokens, stories, and interaction tests.
- V3 supports a generic `DirectoryData[]`, stable item ids, app-supplied strip/search content, desktop collapse, nested expansion, keyboard use, reduced motion, and existing V2 mobile navigation.
- Generated ReScript bindings expose V3's props cleanly, and Euler can consume the published package before any portal migration begins.
